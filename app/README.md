# VLTN Tone Studio (app)

A desktop editor and librarian for the Valeton GP-5, GP-50, the GP-200 family (GP-200, GP-200LT, GP-200JR), the GP-150 and the GP-180, built with Electron 43 (Chromium 150), React 19, TypeScript, Tailwind v4 and shadcn/ui (radix).

The design source is `../design/` (DESIGN.md, the screen specs and the mockups). The pedal protocol code lives in `src/renderer/src/gp5/` (GP-5/GP-50), `src/renderer/src/gp200/` (GP-200 family) and `src/renderer/src/gp150/` (GP-150); those folders are the source of truth.

## GP-5 and GP-50
Both pedals use the same USB-MIDI SysEx protocol, so one `Gp5Session` drives either. The session learns the model from the length of the first active-preset read (0x41 body: 466 bytes GP-5, 511 bytes GP-50) and exposes it as `session.device`; the store keeps it in `useDevice().device` (remembered across launches) and every `PresetState` carries its own `device`.
- Presets: `.prst` is 507 bytes on the GP-5 and 552 on the GP-50 (`gp5/lib/prst.mjs` `DEVICES`); a write is 26 or 29 frames. Writes refuse a preset of the other model; `state/device-model.ts` `prepareForDevice` converts first (GP-5 → GP-50 lossless, GP-50 → GP-5 drops the GP-50-only models, which the confirmation lists).
- Catalog: one merged list (`gp5/lib/catalog-data.mjs`, generated from drewmerc302/valeton-gp50's `fxid_ring.json` + `fxid_ring_gp5.json`). The GP-50 adds PRE AC Sim, PRE C-Wah, CAB AC and tempo-sync params; every lookup in `catalog.mjs` takes the device.
- USB and ports: the device registry (`src/shared/devices.ts`, shared by main, preload and renderer) lists every model with its USB product ids, port pattern, slot count and labels (`07`; GP-200 `12-C`), blocks, SnapTone/IR slots, name length and `.prst` sniffing (`sniffPrst`). Pedal PIDs are `0x0184` (GP-5), `0x018A` (GP-50) and the GP-200 family's below; any other Valeton id is firmware update mode. Empty slots are named after the model. Backups of a GP-50 go to `gp50-…` folders (`<device key>-YYYY-MM-DD`).
- Drivers: `state/device.ts` talks only to a `DeviceDriver` (`state/driver/types.ts`); `Gp5Driver` adapts `Gp5Session` and `MockGp5`, and `state/driver/index.ts` picks the driver by the model's family. The GP-200 family (GP-200, LT, JR: PIDs `0x002A`/`0x002C`/`0x0180`, updater `0x002B`) has `Gp200Driver` over `gp200/lib` (simulator: `?mock=gp200`, `gp200lt`, `gp200jr`), the GP-150 family (GP-150, GP-180: PIDs `0x0186`/`0x0188`) `Gp150Driver` over `gp150/lib` (`?mock=gp150`, `gp180`); all families share one preset model through `state/preset-codec.ts`. GP-150 and GP-180 USB sessions allow editor writes without a special unlock. Presets never convert across families.
- GP-50 provenance: the GP-50 reads, writes and Program Change select were done on hardware by drewmerc302/valeton-gp50; live edits, CC#0 select (listed in the GP-50 manual), SysEx select, SnapTone and User IR uploads follow the shared protocol, and static RE of Valeton Suite 2.1.0 shows Suite sending the same bytes to a GP-50. **Globals differ:** the GP-50 has its own settings table (`GLOBALS_GP50` in `gp5/lib/protocol.mjs`), with other record ids for monitor, BT REC and REC mode and int32 values.
- Experimental pedal commands: `EXPERIMENTAL_FEATURES` (`state/device-model.ts`) lists, per family, the driver features known only from static RE. On a real pedal they stay off until *Settings › Experimental pedal commands* is on (app setting `gp50Extras`); the simulator always has them. GP-5 family: the GP-50's export read, EXP, live tempo, footswitches and order, and in-pedal delete, copy and move. GP-200 family: the Global EQ write. GP-150: none (every command comes from captures of Suite).

## GP-200 family
The GP-200 (R, X), GP-200LT and GP-200JR share one protocol (`gp200/lib`), driven by `Gp200Driver` over `Gp200Session` or `MockGp200`.
- Effect catalog: built in (`gp200/lib/catalog-data.mjs`, generated by `scripts/gp200-catalog-from-studio.mjs` from kabir0st/gp200-studio at a pinned commit, GPL-3.0). The user may replace it with their own `algorithm.xml` (the GP-200 editor's file; *Find automatically* in the desktop app, or *Choose file…*), which adds units, Combox TrueIDs, MinISOff and Auto CAB Match; `gp200/app/catalog-store.ts` builds it and the host keeps it (`shared/host/gp200-catalog.ts`; main `ipc/gp200-catalog.ts`, browser storage on the web). *Use the built-in list* forgets the import.
- Presets: 1224-byte `.prst` (1176 bytes before editor 1.4.0), the same file on all three models; 256 slots (JR 255) labelled `01-A`…`64-D`, 16-character names, no empty slots.
- SnapTones: 10 slots, 0–4 in AMP and 5–9 in DST (`profile.captureBlock`). `Gp200Session.uploadSnapTone` sends record `0x1013` with the 8840-byte clone or a 4744-byte GP-200 blob; a GP-5 family upload file is refused. CAB keeps playing after a SnapTone, so no cab IR is baked in (`noCabIrReason`, `screens/tones/CabIrPicker.tsx`).
- User IRs: 20 slots of 1024 samples (`Gp200Session.uploadUserIr`; a 512-sample GP-5 block is accepted too).
- Tone Match proposes from the catalog in use (built in or imported) and auditions through live edits, so it works on the LT and JR too; the GP-200 cabinet names it picks are a best guess unless an imported list names the amp's cab (Auto CAB Match).

## GP-150 and GP-180
The GP-150 and GP-180 speak one protocol (`gp150/lib`), driven by `Gp150Driver` over `Gp150Session` or `MockGp150`. Nothing tells them apart on the wire, so the driver takes the model from the port name (`Valeton GP-180 MIDI`; anything else of the family is a GP-150); the GP-180 adds footswitch C (`profile.ctrls` 3), which every preset file already holds. Everything comes from the GP-180 USB captures of majabojarska/Valeton-GP180-Rev-Eng (GPL-3.0; `gp150/NOTICE.md`); GP-180 firmware 1.1.1 has passed USB read-only inspection and a complete 200-preset backup. GP-150 hardware and GP-180 writes remain unverified.
- Protocol (`gp150/lib/protocol.mjs`): frames `F0 7F chk | total | offset | seq | index | nibbles | F7`, check byte CRC-8 (poly 0x31) & 0x7F, 119 data bytes per packet, an ACK from the other side for every message and resend requests for lost packets. Logical messages carry their own CRC-8 and a u16 command: `0x1010` names, `0x3011` presets (read with or without select, import), `0x3031`–`0x3033` live block/model/param, `0x3020` tempo/volume/name, `0x2000` settings (records `0x2010` Global EQ, `0x2020`–`0x2050`), `0x1040`/`0x1050` IR and SnapTone uploads. `0x2080` (factory reset) is never built.
- Presets: 1128-byte `.prst` (`gp150/lib/prst.mjs`), 12 modules in module order (PRE WAH DST NS AMP NR CAB EQ MOD DLY RVB VOL) and a chain of any order; 200 slots `001`–`200`, 15-character names, no empty slots (an empty module holds "None", `0x06000003`). The u16 at 0x0E is a checksum of unknown algorithm: edits clear it, imports check layout and chain only.
- Effect catalog: built in (`gp150/lib/catalog-data.mjs`, generated by `scripts/gp150-catalog-from-gp180-re.mjs` from the repo's `effect-wire-schema.json` at a pinned commit; Suite 2.1.0's `module150_data.json`).
- SnapTones: app slots 0–99 are the pedal's list entries 1–100 (0–49 factory, 50–99 user); the upload file is the GP-5 family's 2696-byte one. NS plays in series with AMP and CAB (`snapToneReplacesAmpCab` is false). User IRs: 20 slots, 683 samples at 44.1 kHz as Suite sends them, zero-filled to 2048.
- Settings: `driver/gp150-globals.ts`; a change sends the whole record it lives in. The Global EQ panel uses the GP-200's 31-value order (`gp150EqIndex`); its on/off is the `globalEq` setting, the first value of record `0x2010`.
- Not yet in the app: EXP and knob 1–3 assignments (kept in the preset as they are), NAM uploads (`0x1090`), live chain order (no host command in the captures; order changes reach the pedal with a write). USB ids: `0x0188` (GP-180, from the captures and a driver log, MIDI interface MI_03) and `0x0186` (GP-150, from Windows driver databases); the updaters' ids aren't listed, so like every unknown Valeton id they read as update mode.

Electron is pinned to 43.x because Chromium 152 (Electron 44) breaks WebMIDI SysEx.

## Bluetooth MIDI

Bluetooth MIDI is available for Performance cues, MIDI clock and transport input. Bluetooth editor management is disabled: `useDevice.connect('bluetooth')` rejects before changing the active editor connection. Use USB to inspect or manage the pedal. GP-150 and GP-180 USB editor writes are enabled normally; this does not imply physical write validation.

The Bluetooth store retains completed-write, notification and decoded-message counts for the last session after cleanup. Diagnostics includes these counts in copied and saved reports. See [Bluetooth support and hardware results](../BLUETOOTH.md), [Performance](../PERFORMANCE.md) and [saved songs](../SONG-LIBRARY.md).

## Song performance

Performance combines synchronized stem playback, a song-following metronome, a lyrics/chords reader and optional timed MIDI. The key worker estimates an overall major/minor key from usable guitar, then other harmonic stems or the original mix; the result and a manual correction live in the song options. Lyrics use a separate cancellable Whisper worker. Neither analysis changes audio pitch or MIDI.

The desktop library copies source/stem PCM and stores charts, lyrics and options under unique song IDs. Portable `.tar.gz` backups stream through the main process with a versioned SHA-256 manifest; restore validates the archive and atomically adds new copies with remapped song/playlist IDs. Playlists advance sequentially; loads between songs are not gapless. MIDI port/configuration preferences are global, while cue arming stays session-only. Note-release resets are restricted to channels where this session sent note messages, since CC64 is a GP-180 looper command.

See [the Performance guide and generic screenshots](../PERFORMANCE.md), [storage and playlist behaviour](../SONG-LIBRARY.md) and [review/follow-up notes](../docs/PR-REVIEW.md).

## Branches and releases
- Work happens on `develop`. Merging `develop` into `main` publishes a release: `.github/workflows/release.yml` runs the typecheck and both test suites, builds the `.dmg` (arm64 and x64), the NSIS installer, the AppImage and the `.deb`, and creates GitHub Release `v<version>` with them.
- `<version>` is `version` in `package.json`. Bump it on `develop` before merging; the workflow fails when that release already exists.
- Add a `## [<version>]` section to `../CHANGELOG.md` in the same change. The workflow fails without it, and it puts that section at the top of the release notes, before the install notes (`.github/release-notes.md`) and GitHub's list of PRs.
- The TONE3000 sign-in in release builds needs the repository secret `T3K_CLIENT_ID`.
- Packages are unsigned: macOS Gatekeeper and Windows SmartScreen warn on first launch.
- In-app updates (`src/main/ipc/update.ts`, `src/renderer/src/app/updates.ts`, `overlays/UpdateDialog.tsx`) read the release's `latest.yml` / `latest-linux.yml`, written by electron-builder from `publish` in `electron-builder.yml`. The workflow uploads them with the blockmaps and stops if one is missing or names another version. The release is created as a draft and published once every file is there. Packaged builds check 3 s after launch and every 6 h (*Settings › About* can turn that off). A new version opens a dialog: "Download and install" fetches the installer (electron-updater checks the SHA-512) and restarts into it, unless a pedal job is running or the preset has unsaved changes. "Later" leaves a downloaded update to install on quit. This applies to the Windows installer and the AppImage. macOS (unsigned, so Squirrel.Mac can't update it), the `.deb` and `npm run dev` offer the release page instead. Development runs check only on *Help › Check for updates…*.

## Launch parameters (web build, demos, E2E)
- `?mock=<device key>` connects that simulated model: `?mock` or `?mock=gp5` a GP-5 with the bundled 100-slot backup, `?mock=gp50` a GP-50 with a native bank (GP-50 fixtures as seeds plus generated presets, user slots 55–99 empty), and `gp200`, `gp200lt`, `gp200jr`, `gp150` or `gp180` that model with a generated bank. The Device screen offers "Simulate a …" for every model whose profile has `simulator: true`.
- `?screen=rig|library|tones|device|capture|song` opens that screen. Add `&param=` to pass a value: `device` + `settings` opens Settings, `capture` takes a capture id, and `song` takes the tab (`stems` or `tone`, e.g. `?screen=song&param=tone` opens Tone match; without it Song reopens the tab used last).

## Layout
- `src/main/`: the window, menu, permissions (`midi`/`midiSysex`, audio-only `media`) and CSP. It also has the `app://bundle` protocol and one IPC module per domain in `ipc/`.
- `src/preload/`: exposes the typed `window.gp5host`, using one module per domain. Results unwrap to `HostError`.
- `src/shared/`: the host API types (`host.ts`, `host/*.ts`), the IPC contract, and pure helpers shared across processes.
- `src/renderer/src/`:
  - `app/`: the shell, palette, command bus and toasts
  - `state/`: the device store (`device.ts`, contract in `device-types.ts`), navigation, UI bus and MIDI log
  - `components/gear/`: hardware art with an accessible control layer
  - `components/write/`: the write confirmation and helpers
  - `snaptone/`: NAM A1/A2 → SnapTone conversion in a Web Worker (see below)
  - `song/`: the Song screen's store, decoding, WAV writer and stem separation (see below)
  - `screens/<name>/`: the screens
  - `host/web/`: the browser fallbacks

## SnapTones
`src/renderer/src/snaptone/` reproduces Valeton Suite 2.1.0's NAM → SnapTone converter, so captures go to the pedal without Suite:
- `pipeline.ts`: the model is checked (`shared/nam.ts` `prepareNam`: A1 at the trainer sizes, or A2), the excitation (channel 0 of Suite's `nam_input_wav.wav`) is resampled to the model rate, the model renders it, and `htkpa.ts` measures the pair into the 8840-byte clone.
- `wavenet.ts` + `a1kernel.wasm`: NAM A1 WaveNet with fast tanh, as Suite renders it.
- `a2.ts` + `a2kernel.wasm`: NAM A2. Suite renders a `SlimmableContainer`'s last (full-size) submodel through NeuralAmpModelerCore's A2 fast path. The kernel copies that path's operation order and matches it bit for bit (`a2.test.ts`, reference outputs from NAM core).
- `kernel.ts`: shared host for both kernels (heap, prewarm, 1024-frame blocks). Rebuild the `.wasm` files with `npm run build:wasm` (clang with the wasm32 target).
- `htkpa.ts`: port of Suite's native HTKPA clone and its r8brain resampler. The tests check the whole pipeline against clones made by Suite itself (`gp5/fixtures/snaptone-a1std.clo`, `gp5/fixtures/snaptone-a2.clo`).
- `worker.ts` / `convert.ts`: run it off the UI thread (about 10–20 s).
- The upload is `Gp5Session.uploadSnapTone` (`gp5/lib/snaptone.mjs`): command `11 25`, 146 frames, one ACK each, verified in the 0x24 table.
- Entry points, each ending in a slot picker and a Write button (that press is the confirmation; an occupied slot shows what it replaces):
  - Tones › a TONE3000 NAM tone (`SnapToneSteps`; the slot is linked to the tone);
  - Tones › *Add NAM from disk…*, or a `.nam` opened or dropped while Tones is showing (`LocalNamDialog`; main `tones:readLocalNam` reads a file opened by path; nothing is linked);
  - the capture editor's *Write it to the pedal* for a file opened there (`LocalSend`). A `.nam` opened on any other screen opens the capture editor.

`nam_input_wav.wav` is Valeton's test signal, so it isn't in the repo or in published builds. When it sits in `src/renderer/src/snaptone/fixtures/` (git-ignored), `npm run dev` and local `npm run dist` builds use it automatically (electron-builder `extraResources`; CI checkouts don't have it). Otherwise the app asks for it once ("Choose nam_input_wav.wav…" in the send steps); on Windows and macOS it is also picked up from the Valeton Suite install (Settings › Valeton Suite, hidden on Linux where it has no use). Either way main keeps a checked copy in `userData/snaptone/` (`src/main/ipc/snaptone.ts`). The browser build keeps it in memory. The same fixture copy runs the comparison tests; without it those tests are skipped.

## User IRs
IRs go to the pedal's 20 User IR slots over USB, without Suite. The upload implementation is documented in `gp5/lib/userir.mjs`. It is covered by `MockGp5` tests, and a GP-5 accepted it on 2026-10-10 (all 112 frames ACKed, slot read back from the 0x20 table). Overwriting an occupied slot hasn't been tried on hardware yet.
- `userir/convert.ts` `prepareUserIr` does what Suite does with a WAV: channel 0, r8brain resample to 44.1 kHz (`snaptone/htkpa.ts`), JUCE 24-bit rounding, and the first samples the pedal keeps: 512 on the GP-5 family (11.6 ms), 1024 on the GP-200 family, 683 on the GP-150. Each sample is sent as an int32. A 24-bit / 44.1 kHz file goes through unchanged.
- The upload is `Gp5Session.uploadUserIr` (`gp5/lib/userir.mjs`): command `11 21`, 112 frames, one ACK each. It is verified in the 0x20 User IR table, and `useDevice.uploadUserIr` wraps it.
- Entry points, each ending in a slot picker and a Write button (that press is the confirmation; an occupied slot shows what it replaces):
  - Tones › a TONE3000 IR (`UserIrSteps`; main `tones:prepareIr` downloads the WAV and checks it, then the slot is linked to the tone);
  - a `.wav` opened or dropped outside Song (`LocalIrDialog`);
  - Tone Match's matched IR.
- IR content can't be read back from the pedal. The UI numbers slots 1–20 like the pedal; in code they are 0–19.

## Song: stem splitter
The Song screen (`screens/song/`, store `song/store.ts`) splits a song into stems with Demucs on the user's machine. The user picks a model and a quality before the split (and again from the mixer's "Split again…"); the choice is kept in localStorage (`song/stems/options.ts`), and the mixer says which model and quality made the current stems.
- Models (`SEPARATION_MODELS` in `src/shared/host/song.ts`): each is one or more passes, one ONNX file each (Hugging Face URL at a commit, SHA-256, size, output stems), keeping some of that file's output rows.
  - Standard: `htdemucs_6s`, six stems (drums, bass, other, vocals, guitar, piano), 285 MB, the default. Constant-folded export (kramp/htdemucs-6s-webgpu-onnx), so it runs on WebGPU.
  - Fine-tuned: the `htdemucs_ft` bag, four stems (no guitar, so no Tone match), 4 × 166 MB. Each specialist (StemSplitio/htdemucs-ft-onnx, fp16-stored weights) contributes only its own stem.
  - Best: `htdemucs_ft`'s drums, bass and vocals specialists plus `htdemucs_6s` for guitar, piano and other (the fine-tuned "other" still holds guitar and piano), six stems, 782 MB.
  - StemSplitio's exports keep a `ConstantOfShape` in their iSTFT. onnxruntime-web's WebGPU build can't place it, not even on its CPU fallback, and graph optimisation runs out of wasm32 memory. They run only on the plain WebAssembly build with optimisation off (`runtime: "wasm"`), so their passes use the processor.
- Quality presets: Fast (`apply_model` overlap 0.25, no shifts), Balanced (overlap 0.5, 2 shifts, about 3× the time) and Max (overlap 0.5, 4 shifts, about 6×). Shifts pad the track with up to 0.5 s of silence, separate, shift back and average. The offsets come from a seeded generator, so a split is reproducible.
- No model is bundled. The desktop app downloads a model's missing files one after another in main into `userData/models/` (resumes a `.part` file, checks the hash, then renames it; `src/main/ipc/song.ts`). The browser build keeps each file in Cache Storage, and an interrupted download keeps the files already finished. The model picker shows what is downloaded and deletes a model's files. Files shared with another model go too.
- `song/decode.ts` decodes with WebAudio at 44.1 kHz and makes mono stereo. `song/stems/engine.ts` runs the passes one after another in a worker that holds one ONNX session at a time (`worker-core.ts`): `worker.ts` (WebGPU build, falling back to its WebAssembly runtime when the session can't be created or a run fails, a lost WebGPU device included; the failed chunk is retried) for Standard's file, and `worker-cpu.ts` (plain WebAssembly build) for the fine-tuned files. The worker uses up to 8 threads when the page is cross-origin isolated. `song/stems/demucs.ts` ports Demucs' normalisation, chunked overlap-add and shifts (`apply_model`). It matches PyTorch within 3e-4.
- On an RTX 4070 Ti SUPER, a 30 s clip splits in about 4.3 s with WebGPU, and a 3:51 song in 28 s. On a Ryzen 7 5800X3D (WebAssembly, 8 threads) one 7.8 s chunk takes about 4 s for each model file, and a fine-tuned file takes about 8 s to start.
- Stems export as 16- or 24-bit WAV, four or six files (`song/wav.ts`, `host.song.saveFiles`).
- Audio files dropped on the window open in Song. While Song is showing, a dropped `.wav` is also a song; elsewhere it goes to a User IR slot.

Tone Match (`song/tonematch/`, `screens/song/tonematch/`, every supported pedal): analyses the guitar stem in a Web Worker (1/3-octave silence-gated LTAS, gain class, delay from onset autocorrelation, reverb from note-ending tails), proposes a preset for the connected pedal's catalog auditioned through the Rig's live edits (`screens/rig/edits.ts`, nothing is saved), and designs a 1024-tap minimum-phase cabinet IR (44.1 kHz) from a ~20 s recording of the pedal's USB audio with the CAB block off. "Write to a User IR slot…" sends it over USB (`LocalIrDialog`; the GP-5 family keeps the first 512 taps, the GP-200 family all 1024).

Tone Match also builds a SnapTone from the user's own captures (`song/tonematch/capture-*.ts`, `SnapToneMatchCard`). Candidates are the downloaded TONE3000 NAM models of amp, amp + cab and pedal tones (main `tones:readNam` reads them from `userData/tones/`; one per model name, A2 before A1), plus any the user picks with the Select flow, which downloads the best SnapTone-ready model. There is no search: the free API tier has none. A worker plays seconds 50–70 of Valeton's test signal through each one with the SnapTone renderer (`snaptone/pipeline.ts` `renderNam`, ×0.31 like the conversion). That segment is guitar DI and the part the clone's last IR is fit on. A capture without a cab then goes through a cab IR designed from the stem's LTAS against its render (`irdesign.ts`, no recording needed); one whose TONE3000 gear or NAM `gear_type` includes a cab is compared as it is. Ranking distance = |gain score − stem's| / 0.1 + LTAS residual (100 Hz–6.3 kHz, levelled at 200 Hz–4 kHz) / 6 dB, shown as 100·e^(−D/3). The chosen capture is converted with its IR inside on the GP-5 family (`convertToClone`). On the GP-200 family it is converted without the IR, which goes to a User IR slot for CAB. The clone becomes a Tones send draft at the Write step (`startSendDraft` `built`), so slot, name, write, read-back and link are the Tones flow. The IR can be saved as WAV or written to a User IR slot. Limits: the excitation's level and the stem's mix (compression, EQ, doubled parts) both move the gain score, and a capture is heard at one gain setting.

## TONE3000
Sign-in needs a TONE3000 app key (client_id). Enter it in Settings › TONE3000 account (saved as `clientId` in `userData/tone3000.json`; changing it signs out), or set `MAIN_VITE_T3K_CLIENT_ID` at build time, or `T3K_CLIENT_ID` at runtime. The Settings key wins. See `../design/tone3000.md`. Tokens are encrypted with Electron `safeStorage`. When the OS keychain is unavailable, for example KWallet not initialised, they are kept in memory only.
